[4. DATABASE & STORAGE]
- Database type: MongoDB using Mongoose Object-Relational Model.
- Connection method: mongoose.connect() referenced via `config/db.js` using URI from `.env`.
- Tables/Collections:
  1. User
    - Fields: name (String), email (String), phone (String), role (Enum: user/provider/admin/counter/reception), password (String), organizationId (ObjectId), location (GeoJSON Point).
  2. ServiceProvider
    - Fields: user (ObjectId), businessName (String), phone (String), address (String), location (lat/lng), verifyDocument (String), images ([url, public_id]), status (Enum), pendingEdit (Mixed).
  3. Service
    - Fields: organizationId (ObjectId), serviceName (String), description (String), category (String), approvalStatus (Enum), location (GeoJSON Point), status/isActive (Boolean), certificate (String).
  4. Queue
    - Fields: serviceId (ObjectId), queueName (String), capacity (Number), isActive (Boolean), counters ([ObjectId]), openTime (String), closeTime (String), avgServiceTime (Number), status (Enum).
  5. Ticket
    - Fields: service (ObjectId), queue (ObjectId), user (ObjectId), tokenNumber (Number), status (Enum: waiting, processing, served, cancelled), actualWaitDuration, servedAt, scheduledStart, userLocation (GeoJSON Point).
  6. Counter
    - Fields: name (String), user (ObjectId), service (ObjectId), organization (ObjectId), isActive (Boolean), currentTicket (ObjectId).
  7. QueueHistory
    - Fields: user (ObjectId), service (ObjectId), ticket (ObjectId), tokenNumber (Number), joinTime (Date), servedTime (Date), actualWaitDuration (Number), predictedWaitDuration (Number), status (Enum).
  8. Review
    - Fields: user (ObjectId), targetType (Enum: org, service, queue), targetId (ObjectId), rating (Number), images ([url, public_id]).
  9. Otp
    - Fields: email (String), otp (String), purpose (Enum), expiresAt (Date).
  10. Notification
    - Fields: user (ObjectId), type (Enum), title (String), message (String), read (Boolean), data (Mixed).
- Relationships between entities:
  - Users are associated with ServiceProviders if role is provider.
  - ServiceProviders have many Services.
  - Services have specific Queues.
  - Queues are served by multiple Counters (assigned to specific Staff Users).
  - Tickets bridge Users to Queues and Services.
- Data lifecycle (how data flows): Provider registers -> Approved by Admin -> Provider adds Service -> Approved by Admin -> Provider activates Queue -> User creates Ticket on Queue -> Provider/Counter updates Ticket status -> Automatically moves ticket to QueueHistory upon termination.

[7. SYSTEM BEHAVIOR]
- Queue handling logic: Standard FIFO or scheduled slot overlapping arrays. System auto-calculates `avgServiceTime` * `people_in_front` to project ETAs. Counters pull from array indices using state manipulations.
- Token generation logic: Based on daily resets or incrementing max sequence found in the Queue's active tickets.
- Real-time updates: Handled using Socket.IO instances matching `queue_[QUEUE_ID]`. Socket emissions trigger React UI re-renders on counters shifting.
- State handling: Express acts statelessly. JWT provides identity. Global application reactivity managed by components re-fetching or receiving socket payload dispatches.

[10. TESTING DATA (VERY IMPORTANT)]
Test scenarios:
- Valid user flow: Normal login, successfully create a walk-in token when queue matches active business hours.
- Invalid inputs: Sending empty coordinates on geolocked queues, missing authentication cookies headers on restricted routes `/api/admin/*`.
- Edge cases: Same user joining same queue twice simultaneously; multiple counters hitting `serve-next` at the exact same microsecond (Concurrency race testing); user connection drops when polling ETA.

Performance assumptions:
- Expected response time: High performance under minimal latency. API replies ~50-150ms depending on DB index loads.
- Load handling capability: Due to use of Express and connection pooling in Mongo, acceptable for typical monolithic regional scale requests (e.g. 500-1000 concurrent socket users per instance).

Reliability:
- Expected uptime behavior: Crons run isolated and stateless guards applied (`notifyRunning` locks) against duplicate memory leaks on server. PM2 clustering or Node restarts might sever temporary Socket lines.
- Failure handling: Centralized error handling returns strict structured `{ success: false, message: ...}` instead of exposing sensitive thread dumps.
